# Εξορθολογισμός αρνητικών υπολοίπων αποθήκης — Πρόταση

> Κατάσταση: **πρόταση προς έγκριση** (καμία υλοποίηση ακόμη). Αφορά εγγραφή παραστατικών
> διόρθωσης στο SoftOne — χαλαρώνει τον κανόνα «read-only σε λογιστικά», οπότε θέλει ρητή έγκριση
> και δοκιμή στο stage πριν την παραγωγή.

## 1. Τι είναι το πρόβλημα

Αρνητικό υπόλοιπο = για ένα είδος σε μια αποθήκη, το άθροισμα των κινήσεων βγάζει ποσότητα < 0.
Δηλαδή το σύστημα «πούλησε/ανάλωσε» περισσότερα απ' όσα έχει καταχωρηθεί ότι μπήκαν. **Το υπόλοιπο
δεν είναι πεδίο** — είναι υπολογισμός από τις κινήσεις. Άρα **δεν μηδενίζεται με απευθείας γράψιμο**·
διορθώνεται μόνο με (α) διόρθωση της αιτίας ή (β) νέα κίνηση (παραστατικό διαφορών).

### Γιατί προκύπτει (οι συνήθεις αιτίες — καθορίζουν και τη σωστή διόρθωση)

| # | Αιτία | Σωστή αντιμετώπιση |
|---|-------|--------------------|
| A | **Χρονισμός**: η εκροή (πώληση/ανάλωση) καταχωρήθηκε πριν την παραλαβή | Καταχώριση/διόρθωση **ημερομηνίας παραλαβής** ώστε να προηγείται — όχι απογραφή |
| B | **Λάθος μονάδα/συσκευασία** (π.χ. πούλησες σε τεμ., αγόρασες σε κιβ.) | Διόρθωση γραμμής στο **υπάρχον** παραστατικό |
| C | **Λάθος αποθήκη** (εκροή από αποθήκη που δεν είχε το απόθεμα) | Διόρθωση αποθήκης στη γραμμή, ή μεταφορά μεταξύ αποθηκών |
| D | **Πραγματική διαφορά** (φθορά, κλοπή, λάθος/ελλιπής απογραφή) | **Παραστατικό διαφορών απογραφής** (θετική διαφορά) |
| E | **Ανενεργό/υπό κατάργηση είδος** με υπόλοιπο-σκουπίδι | Μηδενισμός με απογραφή + απενεργοποίηση |

> Το κλειδί: **πρώτα βρίσκουμε την αιτία**, μετά διαλέγουμε διόρθωση. Μαζικός «μηδενισμός» όλων με
> ένα παραστατικό απογραφής κρύβει λάθη χρονισμού/μονάδας που θα ξαναεμφανιστούν και νοθεύει το
> κόστος.

## 2. Τι υπάρχει ήδη στην εφαρμογή (τα ξαναχρησιμοποιούμε)

- **`SoftoneStock`** (mirror: `mtrl`, `whouse`, `qty`) → η ανίχνευση αρνητικών είναι απλό query
  `qty < 0`, τοπικά, χωρίς κλήση SoftOne. (`lib/item-stock.ts`)
- **`softoneFetchStock`** → ζωντανή επαλήθευση ποσότητας πριν γράψουμε (ο καθρέφτης μπορεί να έχει
  παλιώσει).
- **`warehouses()`** → οι αποθήκες (SoftoneLookup kind `WHOUSE`).
- Το pattern κλήσεων SoftOne (two-step auth, cp1253/gzip, `setData` με `LINENUM ≥ 9000001` για νέες
  γραμμές) υπάρχει ήδη στο OCR/PURDOC pipeline.

## 3. Τι παραστατικό γράφουμε στο SoftOne

- **Αντικείμενο: `ITEDOC`** — «Παραστατικά αποθήκης» (EditMaster, κύριος πίνακας `FINDOC`). Είναι το
  σωστό αντικείμενο για κινήσεις/διαφορές αποθήκης (απογραφή, θετικές/αρνητικές διαφορές).
- **Η `SERIES` ορίζει τον τύπο** (π.χ. «Διαφορές Απογραφής — Θετική διαφορά»). Ποια ακριβώς σειρά
  και FPRMS ισχύουν στην εγκατάσταση **kolleris** πρέπει να επιβεβαιωθεί live (open item §7).
- Γραμμές: `MTRL`, `WHOUSE`, `QTY1` (η διαφορά που εισάγουμε), κόστος εισαγωγής, προαιρετικά
  `PRJC/PRJCSTAGE/COSTCNTR` αν η διαφορά αφορά έργο.
- **GL**: δεν τα αγγίζουμε χειροκίνητα — η `SERIES` του ITEDOC φέρνει το λογιστικό υπόβαθρο.

## 4. Το ερωτηματολόγιο (routing ανά είδος/ομάδα)

Για κάθε αρνητικό (ή ομάδα ομοειδών), το wizard ρωτά και δρομολογεί:

1. **«Έχει μείνει παραλαβή ακαταχώρητη ή με λάθος ημερομηνία;»** → δρόμος **A** (διόρθωση αιτίας).
2. **«Είναι λάθος η μονάδα/συσκευασία ή η αποθήκη σε κάποιο παραστατικό;»** → **B/C** (διόρθωση
   γραμμής — το wizard δείχνει τα τελευταία παραστατικά του είδους για εντοπισμό).
3. **«Είναι πραγματική διαφορά (φθορά/κλοπή/απογραφή);»** → **D** (θετική διαφορά ITEDOC).
4. **«Είναι ανενεργό είδος για καθάρισμα;»** → **E** (μηδενισμός + απενεργοποίηση).

Παράμετροι που ζητά για τους δρόμους D/E (που γράφουν ITEDOC):
- **Ημερομηνία** διόρθωσης (έλεγχος: όχι σε κλεισμένη περίοδο — §7).
- **Αποθήκη** (προεπιλογή: αυτή με το αρνητικό).
- **Κόστος εισαγωγής**: προεπιλογή **μέση σταθμική** του είδους (για να μην νοθεύεται το μέσο
  κόστος)· εναλλακτικά τελευταία τιμή αγοράς ή χειροκίνητο.
- **Αιτία/σχόλιο** (υποχρεωτικό — μπαίνει στο παραστατικό και στο audit).

## 5. Η ροή του wizard (βήματα)

1. **Σάρωση** — λίστα αρνητικών: είδος, αποθήκη, ποσότητα, **αξία** (ποσότητα × μέση σταθμική),
   ηλικία, πλήθος. Φίλτρα ανά αποθήκη/κατηγορία/μέγεθος.
2. **Ζωντανή επαλήθευση** — για όσα επιλέξεις, `softoneFetchStock` ώστε να μη διορθώσουμε κάτι που
   ήδη λύθηκε.
3. **Ερωτηματολόγιο** — ανά είδος/ομάδα, επιλογή δρόμου A–E (με «μαζική εφαρμογή» σε ομοειδή).
4. **Προεπισκόπηση** — τι ακριβώς θα γίνει: ποια παραστατικά/γραμμές, ποσότητες, αξίες, **λογιστικός
   αντίκτυπος** (ποια σειρά, τι ενημερώνει). Γραφικό σύνοψης (dataviz) πριν/μετά.
5. **Έγκριση & καταχώριση** — στο stage άμεσα· στην παραγωγή **2 βήματα** (ρητή φράση επιβεβαίωσης),
   `setData` ITEDOC με idempotency key ανά (είδος, αποθήκη, run).
6. **Επαλήθευση** — επανασάρωση: υπόλοιπο ≥ 0, αναφορά τι διορθώθηκε/τι έμεινε, εγγραφή στο audit.

## 6. Λογιστική ορθότητα — οι κανόνες που κλειδώνουμε

- **Ημερομηνία** εντός ανοιχτής περιόδου· διαφορετικά μπλοκ με σαφές μήνυμα.
- **Κόστος** της εισαγόμενης διαφοράς = μέση σταθμική (default), ώστε η διόρθωση ποσότητας να μην
  αλλάζει το μέσο κόστος του είδους.
- **Β' vs Γ' βιβλία**: η σωστή `SERIES` ITEDOC φέρνει τη λογιστική· δεν γράφουμε GL/χαρακτηρισμούς
  χειροκίνητα.
- **Idempotency + audit**: ένα παραστατικό ανά (είδος, αποθήκη, run)· πλήρες audit (ποιος, πότε,
  αιτία, πριν/μετά).
- **Ασφάλεια**: dry-run → stage → production· όρια ποσότητας/αξίας ανά run· 2-step για production.

## 7. Ανοιχτά σημεία (χρειάζομαι απαντήσεις / τον λογιστή)

1. **Ποια `SERIES`/FPRMS** για «Διαφορές Απογραφής» (θετική/αρνητική) στην kolleris; → μπορώ να τα
   τραβήξω **live** (`getSelectorData` σε SERIES του ITEDOC) και να σου τα δείξω για επιλογή.
2. **myDATA**: αυτά τα εσωτερικά παραστατικά διαβιβάζονται ή όχι; (συνήθως όχι, αλλά να οριστεί).
3. **Μέθοδος κοστολόγησης** της εγκατάστασης (μέση σταθμική;) και ποια τιμή για την εισαγωγή.
4. **Κλεισμένες περίοδοι/ΦΠΑ** που περιορίζουν την ημερομηνία διόρθωσης.
5. **Εύρος**: όλες οι αποθήκες ή συγκεκριμένες; Όλα τα είδη ή εξαιρέσεις;

## 8. Υλοποίηση σε φάσεις (πρόταση)

- **Φάση 1 — Ανίχνευση & αναφορά (read-only, ασφαλές, άμεσα χρήσιμο)**: νέα σελίδα π.χ.
  `/admin/items/negative-stock` ή `/admin/softone/negative-stock` — σάρωση `SoftoneStock.qty < 0`,
  κατηγοριοποίηση, αξία, φίλτρα, εξαγωγή. Καμία εγγραφή.
- **Φάση 2 — Wizard με καταχώριση στο stage**: ερωτηματολόγιο A–E, προεπισκόπηση, `setData` ITEDOC
  με τη σωστή SERIES, επαλήθευση — μόνο στο stage, με έγκριση.
- **Φάση 3 — Παραγωγή**: 2-step approval, όρια, πλήρες audit, πριν/μετά αναφορά.

## 9. Τι ΔΕΝ κάνει (όρια)

- Δεν γράφει υπόλοιπο απευθείας (δεν υπάρχει τέτοιο πεδίο).
- Δεν αγγίζει myDATA χαρακτηρισμούς ή GL χειροκίνητα.
- Δεν καταχωρεί σε κλεισμένη περίοδο.
- Δεν κάνει μαζική διόρθωση χωρίς review ανά περίπτωση.
